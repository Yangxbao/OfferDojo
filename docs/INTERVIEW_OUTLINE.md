# 校招面试项目讲解提纲（JobSim AI）

> 用法：这不是背诵稿，是你自己讲项目的"目录"。每节给出讲述顺序和可能被追问的点；讲之前把对应源码再读一遍，确保每个论断都能落到代码。

## 1. 项目解决什么问题（30 秒版本）

"大学生实习前缺少真实工作场景的练习：学校作业偏语法，实习又怕搞砸。JobSim AI 提供人工设计的 Java 后端模拟任务——读需求、做设计、排查问题——提交后由 AI 按预先定义的评分标准给出结构化反馈（分维度得分、正确做法、问题、遗漏的边界情况、改进建议、技术追问、下一步任务推荐），并把历次练习沉淀为个人能力画像。它刻意不是聊天页面，而是围绕完整业务闭环（选任务 → 作答 → 评估 → 复盘 → 推荐）的系统。"

**追问预判**：和直接问 ChatGPT 有什么区别？→ 答：任务与评分标准是预定义且一致的（可对比、可统计）；输出是结构化字段（能聚合出能力雷达/薄弱环节，而聊天记录不能）；系统有用户、任务、历史、权限等真实业务约束。

## 2. 核心业务流程（画图讲）

```
注册/登录 → 任务中心（筛选）→ 任务详情（背景/需求/约束/交付物/验收/评分标准）
  → 保存草稿（自动保存）→ 提交 → AI 评估（Mock/Remote + 降级）
  → 结构化评估报告 → 练习记录/能力分析（趋势、雷达、薄弱环节、完成率）
  → 按薄弱环节推荐下一个任务（闭环）
```

管理端：任务 CRUD + 上下架 + 练习统计 + 评估记录 + AI 调用失败日志。

## 3. 为什么选这些技术（讲"权衡"而不是"名单"）

- **Spring Boot 3.5 + Java 21**：主流生产栈；3.x 生命周期内、生态兼容（springdoc 2.8、MyBatis-Plus boot3 starter 都有对应适配线）——选型前我在 Maven Central 核实了版本对应关系。
- **MyBatis-Plus 而不是 JPA**：国内实习场景主流；统计 SQL 我要精确控制（CAST 日期分组、条件聚合），MyBatis 的 SQL 可控性更适合；BaseMapper + Wrapper 覆盖 80% 简单 CRUD。
- **JWT 而不是 Session**：无状态、前后端分离下简单；主动讲了取舍——localStorage 有 XSS 面、无法服务端吊销，生产应考虑 HttpOnly Cookie + refresh token（ROADMAP 里有）。
- **H2（测试/演示）+ MySQL（开发/生产）**：`mvn test` 在任何机器/CI 秒跑，不依赖外部服务；代价是维护两份等价 DDL，未来用 Testcontainers 合并（这也是我可以讲的真实权衡）。
- **自建 AiProvider 适配层而不是直接引 Spring AI**：项目要求"Spring AI 或兼容适配层"。我选了自建——代码量小（两个实现类）、初学者能逐行理解、避免框架版本强耦合；接口抽象与 Spring AI 的 ChatClient 思想一致，后续替换成本低。

## 4. AI 评分链路如何工作（核心亮点，讲 3 分钟）

1. **输入打包**：`EvaluationContext` 把任务背景/需求/约束/交付物/验收/评分标准 + 学生答案组装成一个 record，Provider 不接触数据库实体——所以 Mock 实现可以脱离数据库做纯单元测试。
2. **Mock 路径**：任务预设了每个维度的关键词提示（mock_hints_json），按"要点命中率"给分（4 + 5×覆盖率 + 篇幅调整，收敛到 [3,10]），亮点/问题/边界/建议按命中情况挑选——**确定性、可复现、可测试**，没有 Key 也能完整演示。
3. **Remote 路径**：OpenAI 兼容 `/chat/completions`；system prompt 限定角色，user prompt 附带任务与答案，**强制 JSON 输出**；解析后逐字段钳制——分数 clamp 到 0-10、维度名必须对齐评分标准（对不上按中性分处理并注明）、推荐任务编码过滤到系统真实存在的任务。
4. **总分不信任模型**：`总分 = Σ(维度分×权重)/Σ权重` 在服务端按任务评分标准计算。
5. **降级**：Remote 的任何失败（TIMEOUT/HTTP_ERROR/PARSE_ERROR，超时用 JDK HttpClient 显式控制）→ 写 `ai_call_log` 失败记录 → 回退 Mock → 评估记录 `provider=MOCK_FALLBACK` + `notice` 降级说明。用户永远拿得到结果，也永远知道结果来源。

**追问预判**：怎么防 Prompt 注入？→ 当前在评估场景风险有限（答案会被当数据而非指令的一部分影响其他用户有限），但严格做法是答案用定界符包裹 + 系统提示明确"以下为待评估材料"；这是我 roadmap 里提示词模板外置时要一并做的。
**怎么评估 AI 评分准不准？**→ 目前靠 Mock 的可解释规则 + 人工复核；计划加"人工复核标记"字段沉淀纠偏数据（ROADMAP 阶段一/二）。

## 5. 如何处理 AI 输出异常（分层答）

- **传输层**：连接超时 10s / 请求超时可配（默认 30s）；非 2xx 抛 `HTTP_ERROR`（日志只留响应片段，不带密钥）。
- **解析层**：去掉 ```json 围栏 → Jackson 解析失败抛 `PARSE_ERROR`；字段级防御：缺维度按中性分补、分数钳制、字符串数组逐项过滤空值、next_task_codes 与任务库交集。
- **编排层**：所有 `AiServiceException` 统一降级 Mock，失败写 `ai_call_log`（后台可查失败记录），用户侧 notice 如实说明。
- **展示层**：评估报告常驻"AI 评分仅供参考，请人工核对技术结论"提示；来源标签区分 本地模拟 / AI 模型 / 降级评估。

## 6. 如何测试关键逻辑

- **单元**：JWT 签发/解析/过期/篡改；MockAiProvider 的确定性评分（好答案 > 差答案、结构完整性、无提示数据的通用路径）；AbilityCalculator 聚合纯函数。单元测试快（毫秒级），覆盖分支矩阵。
- **集成**：`FullFlowIntegrationTest` 用 H2 内存库跑真实 HTTP + Security + MyBatis 链路：401 → 注册 → 登录 → 列表（≥12）→ 草稿覆盖式保存 → 提交评估（断言结构化字段）→ 统计反映真实数据 → 越权 403 → 管理端统计。
- **前端**：Vitest 测工具函数与 Pinia 状态；vue-tsc 全量类型检查 + 生产构建做门禁。
- **CI**：GitHub Actions 两个 job（后端 mvn test / 前端 type-check + test + build）。

**追问预判**：为什么集成测试不用 MySQL？→ 答真实权衡：CI 简单零依赖 vs 环境一致性；H2 用 MySQL 兼容模式覆盖了绝大部分行为，但确实发现不了 MySQL 方言问题——所以我在本机用真实 MySQL 做了手工验证，并把 Testcontainers 列入 ROADMAP。

## 7. 数据库设计要点

5 张表：sys_user / task / task_submission / task_evaluation / ai_call_log。
- 唯一约束：username、task.code、evaluation.submission_id（一次提交一份评估）
- 组合索引按查询形态建：`(user_id, created_at)` 支撑趋势与列表；`(user_id, task_id)` 支撑草稿/状态查询
- 刻意反范式：评估表冗余 user_id/task_id，按人/按任务统计免 JOIN（写多读多的数据才怕冗余，评估是只写的）
- JSON 内容存 TEXT + Java 解析：任务内容与评估结果是整块读写的数据；查询维度都是独立列
- 踩过的坑（真实经历，面试加分）：SQL 脚本 `#` 注释 + Spring 脚本解析器导致 MySQL 静默跳过第一条建表语句；Windows GBK 默认编码对 UTF-8 脚本的影响

## 8. 安全相关实现

- BCrypt 密码哈希；登录失败统一提示防账号枚举
- JWT：HS256 + 环境变量密钥；过滤器静默降级匿名；`/api/admin/**` 路径规则 + `@PreAuthorize` 双重校验
- 数据归属：提交详情在 Service 层比对 userId，防水平越权
- 分页上限（size ≤ 50）、答案长度上限（20000 字）防滥用
- 密钥卫生：API Key 只在请求头；`.env` 进 .gitignore；日志不含密钥

## 9. 当前限制与优化方向（主动说，反而加分）

1. 单机单库，无缓存层——数据量大了以后统计要预聚合（ROADMAP 阶段四）
2. 评估是同步的——超长答案下用户要等；计划 SSE 流式 + 队列化（阶段二）
3. Mock 评分是关键词覆盖率，不是语义理解——它的定位是"没有 Key 也能跑通的演示与兜底"，评分质量靠 Remote 路径
4. 测试环境 H2 与生产 MySQL 不完全一致——Testcontainers（阶段四）
5. token 无吊销机制——refresh token / 黑名单（阶段四）

## 10. 一句话收尾

"这个项目的价值不在 AI 多强，而在于把'AI 能力'装进了一个有真实用户、权限、数据、测试和降级策略的业务系统里——这套工程化思维是我从项目里最大的收获。"
